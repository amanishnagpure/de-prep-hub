## #008 — Large-Scale Order Aggregation

**Slug (proposed):** `large-scale-order-aggregation`  
**Taxonomy:** Performance · Spark Optimization  
**Competency:** Process a deliberately larger dataset within an execution budget.

### Inputs

```text
orders
customers
```

### Task

Calculate customer-level order count and revenue while staying within the execution budget on scaled fixtures.

### Submission classes

| Class | Expected verdict |
|-------|------------------|
| Correct + efficient | ✅ PASS |
| Correct + inefficient | ⚠️ PERFORMANCE (not WRONG ANSWER) |
| Incorrect | ❌ WRONG ANSWER |

**Important:** A correct-but-slow solution must **not** be labeled `WRONG ANSWER`. That semantic distinction matters for an experienced-DE platform.

### Hidden fixtures — stress common DE mistakes

- unnecessary `collect()`
- Python-side loops
- excessive repartitioning
- inefficient joins
- unnecessary materialization
- poor filtering order

Adversarial bad solutions live in the seed module (`adversarial.pyspark`), not the test harness.

### Performance contract (v1 — keep simple)

Do **not** introduce Spark physical-plan analysis for the first version.

```text
Correctness
     +
Runtime/resource threshold
     ↓
Final verdict
```

**Threshold guidance:** Use a **generous, deterministic** budget derived from the reference solution on CI hardware — not tight machine-specific limits. Capture at minimum:

```text
runtimeMs
inputRows
outputRows
```

Later (when execution infrastructure is stable), optional Spark-specific metrics: shuffle bytes, read/write stats, stage counts.

---

## Verdict model (target)

`PERFORMANCE` must be a **first-class verdict status** — not a special-case error message on an otherwise `accepted` or `wrong_answer` result.

```text
Correctness
    +
Performance threshold
    ↓
┌─────────────────────────────┐
│ Correct + within budget     │ → PASS        (status: accepted)
│ Correct + exceeds budget    │ → PERFORMANCE (status: performance)
│ Incorrect                   │ → WRONG ANSWER (status: wrong_answer)
└─────────────────────────────┘
```

Flow:

```text
                    ┌─ Correct ────────→ evaluate performance budget
Submission ─────────┤
                    └─ Incorrect ──────→ ❌ WRONG ANSWER

Correct + within budget  → ✅ PASS
Correct + exceeds budget → ⚠️ PERFORMANCE
```

### Implementation notes (when gate is green)

1. Add `performance` to judge status union (`JudgeVerdict`, challenge types, verdict display).
2. Add reference + adversarial seeds in `scripts/challenge-seeds/large-scale-order-aggregation.mjs`.
3. Extend generic judge to compare `runtimeMs` (and row metrics) against seed-defined budgets **after** correctness passes.
4. Wire verdict UX (`verdict-display.ts`, challenge panel) for first-class PERFORMANCE state.
5. Regression: reference passes; adversarial-correct-slow gets `performance`; adversarial-wrong gets `wrong_answer`.

Architecture invariant: performance thresholds live in seed metadata; keep `de-challenge-judge.ts` generic.
