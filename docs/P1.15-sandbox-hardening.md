# P1.15 — Sandbox Hardening

> **Status:** Implementation complete; deployment/runtime verification pending.
>
> Security PoCs, API limits, hidden-output sanitization, and container definitions are in place and covered by regression tests. The isolated container path has **not** been exercised on every deployment target until Docker/Podman verification (below) is run.

PySpark and DE Challenge judging execute user code server-side. P1.15 adds defense-in-depth: strip hidden fixture data before it reaches clients, reject abusive API payloads, harden the sandbox token filter, and run PySpark inside an isolated container boundary.

## Architecture

```text
/api/code/judge
       ↓
de-challenge-judge.ts   (unchanged — challenge-specific logic stays here)
       ↓
pyspark-runner.ts       (pyspark-worker-pool.ts)
       ↓
[isolated judge container]   ← production boundary (PYSPARK_JUDGE_CONTAINER=1)
       ↓
PySpark (run_judge.py / judge_core.py)
       ↓
sanitize verdict (server-side — hidden rows never returned)
       ↓
PUBLIC-SAFE VERDICT → API → UI
```

Local development may use the **in-process fallback** (spawn Python on the host). That path is acceptable for dev only.

## Environment variables

### Production (required together)

| Variable | Value | Effect |
|----------|-------|--------|
| `SECURITY_HARDENED` | `1` | API payload limits, rate limiting, sandbox token hardening (`_jvm`, `__import__`, …), worker payload size caps |
| `PYSPARK_JUDGE_CONTAINER` | `1` | Route PySpark execution through isolated container instead of host Python |

> **Warning — do not enable production PySpark judging with the in-process fallback.**
>
> Setting `SECURITY_HARDENED=1` **without** `PYSPARK_JUDGE_CONTAINER=1` still runs user code as a host subprocess. Hardening reduces risk but does **not** replace container isolation (no network off, no read-only root FS, no cgroup limits on the host path).
>
> Production must set **both** flags. Treat missing `PYSPARK_JUDGE_CONTAINER=1` as a deployment misconfiguration.

### Optional tuning

| Variable | Default | Purpose |
|----------|---------|---------|
| `PYSPARK_JUDGE_IMAGE` | `de-code-pyspark-judge:latest` | Container image |
| `PYSPARK_JUDGE_CPUS` | `1` | CPU limit per judge run |
| `PYSPARK_JUDGE_MEMORY` | `768m` | Memory limit per judge run |
| `PYSPARK_JUDGE_PIDS_LIMIT` | `64` | PID limit per judge run |
| `PYSPARK_JUDGE_PYTHON` | auto (`miniconda3` / `python3`) | Host fallback Python binary |
| `JAVA_HOME` | auto-detected | Java for PySpark on host fallback |

### Local development fallback

| Variable | Effect |
|----------|--------|
| *(unset)* `SECURITY_HARDENED` | Pre-hardening behavior — security PoCs document gaps; no API rate/size enforcement |
| *(unset)* `PYSPARK_JUDGE_CONTAINER` | Host Python via `scripts/judge/pyspark/run_judge.py` |
| `PYSPARK_JUDGE_DISABLED=1` | Skip PySpark sandbox; fall back to pattern compare |
| `PYSPARK_WORKER_DISABLED=1` | Disable persistent worker pool; one-shot runs only |

## Resource limits

### API layer (`SECURITY_HARDENED=1`)

Defined in `src/lib/judge/sanitize-verdict.ts`:

| Limit | Value |
|-------|-------|
| Max code length | 50,000 characters |
| Max request body | 512,000 bytes |
| Rate limit | 30 requests / 60 seconds per client IP |

### Container layer (`PYSPARK_JUDGE_CONTAINER=1`)

Applied on every `docker run` / `podman run` (see `pyspark-container.ts`):

| Control | Setting |
|---------|---------|
| CPU | `--cpus 1` (override: `PYSPARK_JUDGE_CPUS`) |
| Memory | `--memory 768m` (override: `PYSPARK_JUDGE_MEMORY`) |
| PIDs | `--pids-limit 64` (override: `PYSPARK_JUDGE_PIDS_LIMIT`) |
| Execution timeout | Payload `timeLimitMs` + 15s kill grace |

### In-judge limits (per problem/challenge seed)

Fixture limits (`timeLimitMs`, `maxInputRows`, `maxOutputRows`, `maxFixtureCount`) are passed in the judge payload and enforced inside `judge_core.py`.

---

## Network policy

Container runs use **`--network none`**. The judge container cannot reach the internet or host services.

Host fallback has **no network isolation** — another reason it must not be used in production.

---

## Non-root execution

| Layer | Identity |
|-------|----------|
| Dockerfile | `USER judge` (UID **1001**) |
| Container run | `--user 1001:1001` |
| Capabilities | `--cap-drop ALL` + `--security-opt no-new-privileges` |
| Filesystem | `--read-only` root; writable `/tmp` via `--tmpfs /tmp:rw,noexec,nosuid,size=256m` |

---

## Hidden-output defense

Hidden fixture row data is stripped **server-side** before the API response:

- `scripts/judge/pyspark/judge_core.py` — `sanitize_case_for_client()`
- `src/lib/judge/sanitize-verdict.ts` — challenge/code verdict wrapper
- UI sanitization (`verdict-display.ts`) is a **second layer**, not the primary protection

Clients should never receive hidden expected/actual row payloads.

## Security regression tests

Pre-hardening (documents reproducible gaps):

```bash
npm run test:security-pocs
```

Post-hardening (expects PoCs blocked/sanitized):

```bash
npm run test:security-pocs:hardened
```

PoC coverage:

1. **PySpark sandbox escape** — `spark._jvm` host path leak (pre-hardening); blocked when hardened
2. **Token filter bypass** — `__import__` bypasses substring `BLOCKED_TOKENS`
3. **Payload abuse** — oversized submissions accepted pre-hardening; rejected when hardened
4. **Hidden output** — server-side sanitization verified

## Deployment verification checklist

Run on a machine or CI runner **with Docker/Podman** before treating P1.15 as production-verified.

```text
Build image
   ↓
Start judge (SECURITY_HARDENED=1 + PYSPARK_JUDGE_CONTAINER=1)
   ↓
Run legitimate SQL/PySpark submissions
   ↓
Run security PoCs (hardened mode)
   ↓
Verify network isolation
   ↓
Verify resource limits
   ↓
Verify timeout/kill behavior
   ↓
Verify hidden-output sanitization
   ↓
Run complete regression suite
```

### Step-by-step commands

```bash
# 1. Build image
npm run judge:pyspark-image

# 2. Export production flags for the app process
export SECURITY_HARDENED=1
export PYSPARK_JUDGE_CONTAINER=1

# 3. Regression — legitimate submissions must still pass
npm run test:de-challenges      # 35/35
npm run test:judge-engine       # 14/14
npm run test:sql-fixtures       # 100/100
npm run test:sql-judge          # 15/15
npm run test:pyspark-judge      # 3/3

# 4. Security — previously successful PoCs must fail safely
npm run test:security-pocs:hardened   # 4/4 blocked/sanitized

# 5. Build
npm run build
```

### What “good” looks like in the container

The valuable signal is not merely that Docker starts. It is that:

- **Legitimate PySpark submissions still pass** inside the container
- **Previously successful PoCs fail safely** (blocked escape, rejected oversized payload, sanitized hidden output)

Optional manual checks:

```bash
# Network isolation — should fail to reach external hosts
docker run --rm --network none de-code-pyspark-judge:latest \
  python3 -c "import socket; socket.create_connection(('1.1.1.1', 53), 2)"

# Non-root — expect uid 1001
docker run --rm de-code-pyspark-judge:latest id -u
```
